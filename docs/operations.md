# 運用手順

## 最初に決めること

利用者への保存方針・問い合わせ先を用意します。現状の回答はフォームが削除されるまで保持し、フォーム削除後は30日後に削除対象です。公開リンクと控えリンクはURLを知る人がアクセスできます。この仕様を公開時に案内してください。

## 削除の復元

削除から30日以内に対象アカウントとフォームIDを確認し、運用者が `deleted_at` をNULLに戻します。受付は `closed` のままにし、作成者が内容を確認してから再開します。復元UIはありません。30日を超えたデータはバックアップの保存期間に従います。

## Cronと容量

Vercel Cronの `/api/maintenance` は `Authorization: Bearer CRON_SECRET` を要求します。失敗とキューの滞留を監視してください。APIを公開URLから無認証で手動実行することはできません。

実行は毎日04:00 JST。1回500オブジェクトまでなので、結果の `morePossible` が続く場合は頻度・バッチ数を調整します。稼働状況に応じてVercel / Supabaseの使用量アラートを設定します。登録原本の上限と、一時ファイルを含むStorage全体の使用量は別です。

## バックアップと復元確認

SupabaseのDBバックアップにはStorageのPDF本体が含まれません。DBと原本ファイルを別々に保管します。[公式の範囲](https://supabase.com/docs/guides/platform/backups)

- DB：利用プランのバックアップ・復旧機能を確認し、CLIのDB dump等も使って別の保存先に保管する。
- PDF：非公開の原本をStorage API / S3互換API等で別の非公開ストレージへコピーする。一時出力は再生成できる。
- 認証・設定：Authの設定、SMTP、ドメイン、Turnstile、環境変数の復元方法を管理する。秘密値はパスワードマネージャー等へ保管する。
- 復元検証：別環境で所有者のフォームを開き、原本の対応、回答と版、記入済みPDFの再生成、公開リンクの受付停止状態を確認する。

バックアップの自動保管先は利用者のアカウントが必要です。このリポジトリがバックアップを外部へ自動転送することはありません。

## 更新

検証用の別プロジェクトで移行SQLを適用し、`npm test`・`npm run test:cloud`、メール・Turnstile・PDFの確認を終えてから本番へ適用します。破壊的なスキーマ変更は、旧アプリと新アプリが同時に動く期間も考慮して段階的に行います。

## 記録と秘密値

アプリの一般エラーログには回答・メールアドレス・PDF・Secret keyを出しません。Vercelのアクセスログ等には共有トークンを含むURLが記録される可能性があるため、ログの閲覧権限と保存期間も制限してください。署名URLや回答控えURLを公開Issueへ貼らないでください。

秘密キーの漏えいが疑われる場合は対象キーをローテーションし、環境変数を更新して再デプロイします。SupabaseのSecret keyとTurnstile / Cronのキーはそれぞれ別に管理します。
